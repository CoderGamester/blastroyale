# Core connection task completion boundary

The ordinary Home flow reached `MainMenuState.LoadMainMenu` twice and the real `GameLovers.Services.Installer.Bind<IMainMenuServices>` correctly rejected the second binding. The cause is synchronous completion of `CoreLoopState.WaitForPhotonConnection`, not duplicate Core entry and not an installer recovery problem.

The maintained Statechart's `TaskWaitState.InnerTaskAwait` marks completion and recursively calls `Statechart.MoveNext`. When the connection task completes immediately, this nested call advances through no-pending Reconnection into menu loading; the original `TaskWaitState.OnTrigger` then returns its completed transition to the outer caller, which processes the same branch progression again. `InnerStateData` is a reference type, so its current state can change while that original trigger is still on the stack. The duplicate menu load begins before its asynchronous audio/scene work finishes.

The isolated patch adds `await UniTask.NextFrame()` before the existing Photon readiness loop. This guarantees that an already-connected task first returns incomplete and finishes after the original trigger has returned. Photon readiness conditions, connection waiting, menu setup and the installer's duplicate-binding invariant stay intact. The patch does not modify the maintained package.

A real Unity 6000.3.26f1 Play Mode fixture uses the actual pinned Statechart, UniTask and Services installer. Its four-branch Core split contains ConnectionWait, nested no-pending Reconnection and nested menu loading with an actual pending UniTask after Bind. The original connected case produces two bind attempts and the native duplicate-key/task errors. With the frame boundary, both already-connected and initially-disconnected cases produce one bind attempt and zero fixture errors. Core entry count is one in every case. This directly supports the reentrant progression explanation and corrects the earlier suspicion that Core itself entered twice.

Evidence: [native result](verification/core-taskwait-native-causality-proof.json), [guarded integration handoff](verification/core-taskwait-integration-handoff.json), and the original/corrected fixture in `Tools/Validation/CoreTaskWaitCausality`. The owned older clone retains unrelated metadata/import diagnostics; the negative control deliberately logs its two expected errors. The evidence claims zero C# diagnostics and zero errors for the two corrected fixture cases, not globally clean startup of that older clone. Root's complete Main Home-to-match run remains the acceptance check.

This is a bounded application workaround for the exposed connection task. Other synchronous completed task actions can encounter the same maintained Statechart reentrancy defect and should receive a separately validated boundary or an upstream run-to-completion fix when encountered.
