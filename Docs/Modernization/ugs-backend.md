## Identity and persistence

`UnityCloudLoginProvider` calls the native Authentication SDK anonymously, reusing its cached session token. It projects the real UGS PlayerId/name into the existing genuine `LoginResult` DTO only because current hook and server-SDK contracts still consume that DTO. It creates no PlayFab ticket, settings or cloud transport. `UnityCloudHook` initializes config/Friends and publishes the UGS name; it no longer creates a second anonymous identity or a PlayFab-ID directory.

`UnityCloudPlayerStateBackend` is constructed by the original `GameBackendService`. It loads and saves twelve existing models: PlayerData, LiveopsData, CollectionData, IdData, RngData, EquipmentData, BattlePassData, TutorialData, ContentCreatorData, PlayerStoreData, EventsData and BundlePurchaseData. Each is a JSON string under `model_<type>` in Cloud Save's **Default** player-data access class. AccountData, device IDs, session tokens and local settings are excluded. Missing models are initialized, including a stable FNV seed derived from the UGS player ID. Invalid nonempty models fail the existing model parse before replacing live data or running initialization commands.

The native SaveItem write locks from load/successful save are retained and supplied in subsequent writes. Changed keys are saved in one native batch. A conflicting existing key is rejected; the client does not bypass its lock or overwrite another device's change. New keys have no lock, as required by the native API; simultaneous creation is therefore not an independently validated transaction. Failed queued snapshots remain pending, and current retry policy requires another command. No conflict-merge UI or persisted offline queue is claimed. [Unity write-lock behavior](https://docs.unity.com/en-us/cloud-save/concepts/write-locks).

One shared `UgsAccountSession` captures the actual player ID and generation. Native SignedIn, SignedOut, Expired and PlayerIdChanged events invalidate old work, including sign-out/relogin to the same ID. Saves, profile operations and authentication steps validate the capture before dispatch and after awaits. The actual Cloud Save SDK captures the player ID when constructing its request. Queue completion can only dequeue its exact original head; it cannot consume a new account's queued work.

Public player_name, avatar_url and trophies are separate **Public** player-data values. Public profile reads target the requested UGS ID directly. Default is readable/writable by its owner; Public is readable by other players and writable by its owner. Server-only Protected data is intentionally not used for client-computed progression. Cloud Save allows 2000 keys and 5 MiB per player per access class. [Unity player-data classes and limits](https://docs.unity.com/en-us/cloud-save/concepts/player-data).

## Recoverable accounts

Optional recovery uses the actual hosted Unity Player Accounts flow. The provider subscribes to SignedIn/SignInFailed before StartSignInAsync and awaits token-ready completion, with a five-minute bounded wait. Linking calls LinkWithUnityAsync without force-linking. It preserves the exact guest UGS ID, loaded models and pending saves; it does not reload an older cloud snapshot. Signing into another hosted account changes the SDK identity and runs the normal full state reload. Old PlayFab progress is not automatically imported.

Authentication3.8 already includes the dedicated Player Accounts assembly; the game adds `Unity.Services.Authentication.PlayerAccounts`. SDK configuration uses `Resources/UnityPlayerAccountSettings.asset`, created by the native Services > Unity Player Accounts configuration panel. Its actual serialized settings include clientId, scopeMask and optional custom scheme/host. No local JSON ClientId is invented. The Unity Dashboard identity provider must include PC for Editor testing, desktop `http://localhost/callback`, and default mobile `unitydl://com.unityplayeraccounts.<UnityProjectId>`. Missing settings disable the optional account route while guest play remains available. [Official hosted account setup and native sign-in/link API](https://docs.unity.com/en-us/authentication/unity-player-accounts).

Legacy email/password/reset methods explicitly reject the retired flow; account screens now offer guest continuation and the real hosted account route. Logout preserves the cached guest token rather than orphaning unlinked progression. User-requested game-account deletion first deletes Default/Public Cloud Save data and then calls Authentication.DeleteAccountAsync. These are separate requests and may fail partway through; deletion of a hosted Unity Player Account itself uses its provider's separate account management flow.

## Development economy and capacity

The original local progression/shop commands remain client authoritative. Native Cloud Save persistence provides no independent cheat prevention or validated currency grants. Public trophy publication is a separate request from the progression batch. Real money receipt/grant operations remain disabled. Genuine old server DTO names remain temporarily for compatibility, but no operational PlayFab API may remain in the connected client path.

Unity Economy stopped accepting new project signups on 2026-09-08, so adding its SDK would not satisfy fresh-project setup. The authorized scope retains the existing local virtual exchange and progression models instead. [Official Economy service status](https://docs.unity.com/en-us/economy/index).

Checked 2026-10-14: Authentication and Remote Config are free; Cloud Save's free allowance is 5 GiB stored data plus 1 million reads and 1 million writes per month; Lobby allows 10 GiB per month per regional group; Friends allows 50,000 monthly active users. These are finite allowances, not unlimited free hosting. No billing upgrade is performed by this patch. Dashboard-specific enablement and account eligibility still require human verification. [Current Unity pricing](https://unity.com/products/gaming-services/pricing).
